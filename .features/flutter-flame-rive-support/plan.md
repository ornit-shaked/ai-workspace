# Plan — Flutter Plugin: Flame and Rive Support

**Source:** [spec.md](spec.md) (authoritative design) · [feature.md](feature.md) (acceptance criteria)

## Waves

### W1 — Shared installer foundation
**Goal:** Two independent skills can share `pluginName: 'flutter'` without one falsely appearing "already installed" to the other.

Covers spec.md D8 only: `componentId` parameter, component-scoped tracking marker, append-not-overwrite tracking-file write, version bump across the plugin's manifests. Nothing Flame/Rive-specific ships in this wave — it's purely infrastructure the other two depend on.

### W2 — Flame profile
**Goal:** `setup-flame` installs independently end-to-end and satisfies every Flame-side acceptance criterion on its own.

Covers D1 (`rules/flame.md`, including the `flame_tiled` guidance), D3 (skill: ADR, dirs, pubspec deps + asset declarations, example + test), the Flame half of D6 (README), and the Flame half of D5 (confirming no lint changes needed).

### W3 — Rive profile
**Goal:** `setup-rive` installs independently end-to-end and satisfies every Rive-side acceptance criterion on its own.

Covers D2 (`rules/rive.md`), D4 + D4a (skill: ADR, dirs, pubspec deps + asset declarations, the one real fixture `.riv`, example + test), the Rive half of D6 (README), and the Rive half of D5 (confirming no lint changes needed, mirroring W2). The fixture `.riv` is the one deliverable in this wave that isn't code — it's authored in the Rive Editor/CLI, not generated — so it's the critical path for this wave's test strategy (nothing in W3 can be verified end-to-end until it exists).

### W4 — Cross-cutting integration
**Goal:** Flame and Rive coexist cleanly regardless of install order, and every acceptance criterion in spec.md §4 passes against a real scaffolded project, not just each profile in isolation.

Covers D7 (integration guide, declared identically in both manifests), verification of the combined tracking file (D8) after both install, and a correctness pass on D1's `flame_rive` bridge note (documentation only — no new bridge code, per spec's "upstream-first" principle).

## Dependency Graph

```
W1 (installer foundation)
 ├─→ W2 (Flame profile)
 └─→ W3 (Rive profile)
          W2 ─┐
          W3 ─┴─→ W4 (cross-cutting integration)
```

- W2 and W3 do not depend on each other — either can run first, or in parallel, once W1 lands.
- W4 cannot start meaningfully until both W2 and W3 are installable, since it tests their combination.
- No cycle: W1 is the only cross-wave dependency; W4 is a pure sink.

## Risk Register

| # | Risk | Mitigation |
|---|------|------------|
| 1 | W1 touches `plugins/_shared/installer.js`, used by every plugin (`brain`, `lifecycle`, base `setup`) — a regression there is silent and wide-reaching. | Default `componentId` to `pluginName` so existing single-component plugins see byte-identical behavior; re-run `brain`/`lifecycle`/base-`setup` install flows before W2/W3 start, not just after the whole feature ships. |
| 2 | The fixture `.riv` (W3) can't be generated by an agent or script — it needs a human or the Rive Editor/CLI, and it's the critical path for W3's own tests. | Produce the fixture first within W3, before writing the example widget/test against it, so the rest of W3 isn't blocked waiting on it. |
| 3 | Pinned versions (`flame`, `rive`, `flame_bloc`, `flame_test`) in spec.md were checked against pub.dev at spec time, not implementation time, and may have moved. | Re-check pub.dev immediately before W2/W3 start pubspec work — spec.md already flags this as an open decision, not an assumption to carry forward blindly. |
| 4 | D7's integration guide is declared identically in two separate manifests (W2 and W3); if the two copies drift, installing in different orders produces different content. | Both manifest entries point at one shared template source file, not two independently maintained copies — enforce this in W4's review, since it's the wave where both skills' manifests are visible together. |
| 5 | ADR numbering (`ADR-00NN-*`) is a placeholder in spec.md; two other in-flight features in this repo (`doc-governance`, `usage-cost-optimization`) may also be adding ADRs concurrently. | Assign actual ADR numbers at the start of W2/W3 implementation (not now), by checking `docs/adr/ui/` at that moment. |
| 6 | The shared-installer contract requires a version bump across five separate manifest/plugin files per `plugins/AGENTS.md`'s rule; missing one means `claude plugin update` won't deliver the fix to already-installed users. | Treat the five-file bump as a single checklist item in this feature's Definition of Done, not an incidental step inside W1. |
| 7 | Rive CLI flags are explicitly unverified in spec.md (Open Decision #4); a future contributor might be tempted to add a quick `rive --verify` call to a script during W3. | `rules/rive.md`'s caveat already prohibits this; treat any PR that shells out to `rive` with unverified flags as a review-blocking finding, not a style note. |

## Rollout Strategy

**Staged, opt-in — no canary needed.** This is developer-tooling scaffolding, not a runtime product feature; nothing is forced on an existing project.

1. Ship **W1 alone** first, as a plugin version bump with no new skills exposed yet. Verify it against existing `brain`/`lifecycle`/base-`setup` installs in a scratch project — this is the regression-risk wave (Risk #1) and should be confirmed safe in isolation before anything depends on it.
2. Ship **W2 + W3 + W4 together** as the feature release once all three are complete — shipping Flame without Rive (or vice versa) would leave D7's cross-cutting integration guide half-meaningless and some acceptance criteria (the combined-tracking-file ones) unverifiable. The two skills are independently *installable* by end users, but not independently *releasable* as a complete, reviewed unit.
3. No feature flag mechanism exists in this plugin system (skills are either present in a plugin version or not) — "rollout" here means "plugin version a project chooses to update to," which is already opt-in by nature of `claude plugin update`.

## Test Strategy by Wave

| Wave | Unit / mechanical | Integration |
|------|---|---|
| W1 | Re-run installer logic against a plugin with a single component (unchanged `componentId` default) and confirm identical tracking-file output to before the change. | Fresh scratch-project install of `flutter@latest` (base `setup` only) — confirm no regression. |
| W2 | `flutter analyze --fatal-infos`, `flutter test` on the Flame example/test, pubspec asset declarations resolve via `flutter pub get`. | Fresh scratch-project install of `setup-flame` alone; re-run it to confirm idempotency. |
| W3 | Same analyze/test/pub-get checks for the Rive example; widget test specifically exercises the fixture's state-machine boolean flip (spec.md D4a), not just the error path. | Fresh scratch-project install of `setup-rive` alone; re-run it to confirm idempotency. A manual visual spot-check of the fixture's animation in a running app is the one check that can't be automated. |
| W4 | N/A (this wave is integration by definition). | Install both skills in both orders (Flame-then-Rive, Rive-then-Flame) in separate scratch projects; confirm the combined tracking file has both component sections, both READMEs and the single shared integration guide exist in every order, and `flutter analyze`/`flutter test` stay green with both dependency sets present. |

## Feature-Level Definition of Done

- Every acceptance criterion listed in spec.md §4 passes against a real scaffolded Flutter project — not just asserted by an installer unit test — for: Flame alone, Rive alone, and both together in each install order.
- `npm run sync-shared:check` is green (W1's installer change is properly propagated to all three plugins' vendored copies).
- Plugin version bumped consistently across `plugins/flutter/.claude-plugin/plugin.json`, `.devin-plugin/plugin.json`, and all three skills' `manifest.json` files (base `setup`, `setup-flame`, `setup-rive`).
- No regression in `brain`, `lifecycle`, or base `setup`'s existing install behavior (Risk #1, verified in W1 before W2/W3 begin).
