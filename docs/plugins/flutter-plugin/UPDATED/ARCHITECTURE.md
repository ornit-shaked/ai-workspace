# Architecture — Flutter Delta Plugin

**Purpose:** High-level architecture vision and design principles.  
**Status:** Living document — updated when architecture evolves.  
**Last Updated:** 2026-08-07

---

## 1. Architecture Vision

Flutter Delta is a **project bootstrap plugin** that wraps and extends the official Flutter ecosystem. It does not replace, fork, or duplicate upstream content — it only supplies the project-specific delta on top of it.

```
Official Flutter Ecosystem   ← upstream source of truth
        +
Official Dart Ecosystem      ← upstream source of truth
        +
Flutter Delta                ← this plugin (project-specific)
        =
Ready-to-use Flutter workspace
```

### Responsibility Split

| Layer | Responsibility | Examples |
|-------|----------------|----------|
| **Official Flutter Ecosystem** | Flutter knowledge, skills, MCP, architecture guidance, rules, workflows | flutter/agent-plugins, Flutter Architecture Guide, Flutter AI Rules, Flutter MCP Server |
| **Official Dart Ecosystem** | Dart skills, testing, coverage, analysis, mocks | dart-lang/skills, Dart SDK tools |
| **Flutter Delta** | Project-specific decisions, project governance, project bootstrap | Bloc/Cubit override, Freezed Everywhere, very_good_analysis, flavors, ADRs, folder skeleton |
| **Project Brain** (separate plugin) | Memory, learning, cross-project intelligence | Task tracking, session history, lesson capture |

**Key Insight:** The workspace itself is the product. Applications are generated from the workspace.

## 2. Design Principles

### 2.1 Upstream First

**Never duplicate official Flutter/Dart ecosystem content.**

- Reference, don't copy
- Install upstream dependencies automatically
- Point to upstream documentation
- Override only when necessary and document why

**Examples:**
- ✅ Install `flutter/agent-plugins` and reference its skills
- ❌ Copy skill implementations into Flutter Delta
- ✅ Link to Flutter Architecture Guide in CLAUDE.md
- ❌ Duplicate architecture guidance in Flutter Delta docs

### 2.2 Idempotent Operations

**All operations must be safe to re-run.**

- Installing twice produces the same result as installing once
- No duplicate content in `pubspec.yaml`, `CLAUDE.md`, or other files
- Reinstalling skips already-present files
- Version upgrades apply three-way merge for user-modified files

**Examples:**
- ✅ Check if dependency exists before injecting into `pubspec.yaml`
- ✅ Skip file copy if target already exists
- ✅ Detect user modifications via file hash comparison

### 2.3 Non-Destructive

**Never overwrite user-modified content.**

- User code takes precedence over plugin templates
- Three-way merge for conflicts
- Explicit user choice for breaking changes
- Feature code (`lib/ui/features/*`) is never touched

**Examples:**
- ✅ Skip `CLAUDE.md` if user has modified it
- ✅ Three-way merge for rule files on upgrade
- ❌ Overwrite user's custom repository implementations

### 2.4 Traceable

**Every decision documented with source references.**

- All architectural decisions have ADRs
- All decisions traced to upstream sources in Decision Source Matrix
- All assets have clear ownership in Ownership Matrix
- All updates follow documented strategy in Upstream Update Strategy

**Examples:**
- ✅ ADR-0001 documents Bloc/Cubit decision with rationale
- ✅ Decision Source Matrix links to Flutter Architecture Guide
- ✅ Ownership Matrix clarifies who owns `flutter_bloc` package

## 3. Flutter Delta Definition

Flutter Delta contains **only** the following items. Each item is here because it is not covered upstream or is a project-specific override.

### 3.1 Bloc/Cubit Override

**What:** Use Bloc/Cubit for state management instead of Flutter's default ChangeNotifier  
**Why:** Explicit event → state contract and strict testability  
**Source:** [ADR-0001](../../plugins/flutter-plugin/project/.claude/adr/ADR-0001-state-management-bloc.md)

### 3.2 Freezed Everywhere

**What:** Use Freezed for domain models, DTOs, Bloc states, and Bloc events  
**Why:** Extends upstream Freezed usage beyond models to states/events  
**Source:** [ADR-0002](../../plugins/flutter-plugin/project/.claude/adr/ADR-0002-freezed-everywhere.md)

### 3.3 very_good_analysis

**What:** Stricter linting baseline than default `flutter_lints`  
**Why:** Enforce higher code quality standards  
**Source:** [ADR-0003](../../plugins/flutter-plugin/project/.claude/adr/ADR-0003-linting-very-good.md)

### 3.4 Flavors (dev / staging / prod)

**What:** Three explicit environments from day one  
**Why:** Environment separation not generated by official skills  
**Source:** [ADR-0004](../../plugins/flutter-plugin/project/.claude/adr/ADR-0004-flavors.md)

### 3.5 Bootstrap Structure

**What:** Consistent starting folder layout (config/, routing/, data/, domain/, ui/)  
**Why:** AI needs structure before writing first feature  
**Source:** [ADR-0005](../../plugins/flutter-plugin/project/.claude/adr/ADR-0005-folder-structure.md)

### 3.6 ADRs

**What:** Architectural Decision Records for every deviation from Flutter defaults  
**Why:** Auditability and traceability  
**Source:** [ADR-0006](../../plugins/flutter-plugin/project/.claude/adr/ADR-0006-adr-process.md)

### 3.7 Project Rules

**What:** Path-scoped rules in `.claude/rules/*.md`  
**Why:** Enforce project overrides at agent level without re-prompting  
**Source:** [ADR-0007](../../plugins/flutter-plugin/project/.claude/adr/ADR-0007-project-rules.md)

### 3.8 Governance Files (CLAUDE.md + AGENTS.md)

**What:** Top-level rules files for Claude Code and Devin  
**Why:** Multi-agent compatibility with mirrored content  
**Source:** Spec §7.8

### 3.9 Dependency Scaffold

**What:** Required project defaults in `pubspec.yaml`  
**Why:** Upstream does not opinionate on this dependency set  
**Packages:** `flutter_bloc`, `bloc_test`, `freezed`, `freezed_annotation`, `json_annotation`, `json_serializable`, `build_runner`, `go_router`, `provider`, `very_good_analysis`

## 4. Installation Architecture

### 4.1 Plugin Structure

```
plugins/flutter-plugin/
├── manifest.json              # Plugin metadata and file mappings
├── hooks.js                   # Plugin-specific hooks (preInstall, postInstall, contentTransformers)
├── project/                   # Project-scoped templates
│   ├── CLAUDE.template.md
│   ├── AGENTS.template.md
│   ├── .claude/
│   │   ├── rules/             # Path-scoped rules
│   │   └── adr/               # Architectural Decision Records
│   ├── lib/                   # Layered skeleton
│   ├── test/                  # Test structure
│   └── testing/               # Shared fakes
└── docs/                      # Plugin documentation
    ├── DECISION_SOURCE_MATRIX.md
    ├── OWNERSHIP_MATRIX.md
    ├── UPSTREAM_UPDATE_STRATEGY.md
    └── ARCHITECTURE.md (this file)
```

### 4.2 Installation Flow

1. **Verify upstream dependencies**
   - Check for `flutter/agent-plugins`
   - Check for `dart-lang/skills`
   - Check for Flutter MCP configuration

2. **Auto-install missing dependencies**
   - Run `npx skills add @flutter/agent-plugins` if missing
   - Run `npx skills add @dart-lang/skills` if missing
   - Provide manual instructions if auto-install fails

3. **Deploy project files**
   - Copy templates to target project
   - Render placeholders (`{{APP_NAME}}`, `{{PACKAGE_NAME}}`, etc.)
   - Skip existing files (idempotency)
   - Apply content transformers (Dart import sorting, pubspec dep sorting)

4. **Inject dependencies**
   - Add `pubspec_deps` to `pubspec.yaml`
   - Sort dependencies alphabetically
   - Preserve user-added dependencies

5. **Verify installation**
   - Run `flutter pub get`
   - Run `flutter analyze`
   - Create marker file `.flutter-delta.installed`

### 4.3 Hook System

Flutter Delta uses the plugin hook system for custom behavior:

**`preInstall(context)`:**
- Verify Flutter SDK is installed
- Check Flutter version compatibility
- Validate target project structure

**`postInstall(context)`:**
- Run `flutter pub get`
- Run `dart run build_runner build --delete-conflicting-outputs`
- Display installation summary

**`contentTransformers`:**
- Dart import sorter (alphabetical, package imports first)
- pubspec dependency sorter (alphabetical within sections)

## 5. Upgrade Architecture

### 5.1 Version Detection

- Check for `.flutter-delta.installed` marker file
- Compare installed version vs. new version
- Determine upgrade path (patch / minor / major)

### 5.2 Upgrade Strategies by Asset Type

| Asset Type | Strategy | User Protection |
|------------|----------|-----------------|
| Rules | Three-way merge | User edits preserved |
| ADRs | Append only | Never rewrite existing |
| analysis_options.yaml | Overwrite if unchanged | Skip if modified |
| Flavor entry points | Re-render if greenfield | Skip if modified |
| Folder skeleton | Create missing only | Never delete |
| CLAUDE.md / AGENTS.md | Three-way merge | User sections preserved |

### 5.3 Breaking Changes

- Major version bump (e.g., 1.x → 2.x)
- CHANGELOG.md documents migration steps
- Upgrade guide provided
- User opts-in explicitly

## 6. Testing Architecture

### 6.1 Test Levels

**Unit Tests:**
- Installer logic (file copying, template rendering, placeholder substitution)
- Hook system (preInstall, postInstall, contentTransformers)
- Dependency injection (pubspec.yaml manipulation)

**Integration Tests:**
- Full install into empty directory

- Upgrade (user-modified files)

**Validation Tests:**
- `flutter analyze` passes

- `dart run build_runner build` succeeds

## 7. Governance Architecture

### 7.1 Decision Traceability

Every architectural decision is:
1. Documented in an ADR (`docs/adr/ADR-NNNN-*.md`)
2. Traced to source in Decision Source Matrix
3. Linked to owner in Ownership Matrix
4. Governed by update strategy in Upstream Update Strategy

### 7.2 Documentation Hierarchy

```
README.md                          # User-facing: What, Why, How
├── ARCHITECTURE.md (this file)    # Architecture vision and principles
├── DECISION_SOURCE_MATRIX.md      # Traceability: decision → source
├── OWNERSHIP_MATRIX.md            # Ownership: asset → owner → update mechanism
├── UPSTREAM_UPDATE_STRATEGY.md    # Update policy for all dependencies
└── CHANGELOG.md                   # Version history and migration guides
```

## 8. Future Architecture Considerations

### 8.1 Multi-Plugin Composition

**Challenge:** Only one `CLAUDE.md` can exist per project  
**Current:** Flutter Delta overwrites on install  
**Future:** Composition mechanism where `CLAUDE.md` includes plugin-specific files

**Potential Solutions:**
- `CLAUDE.md` as router → includes `CLAUDE-flutter.md`, `CLAUDE-fastapi.md`
- Rule registry (YAML/JSON) aggregating rules by plugin
- Separate files merged at install time

**Status:** Deferred to v1.1 (see lessons in `.project-brain/inbox/lessons.md`)

### 8.2 Validation Hooks

**Current:** `preInstall` and `postInstall` hooks  
**Future:** Additional lifecycle hooks:
- `validate(context)` — check project state before install
- `resolveConflicts(context)` — handle file overwrites
- `postDeploy(context)` — run tests, generate docs

**Status:** Extensibility designed into hook system; add as needed

### 8.3 Plugin Marketplace

**Current:** Manual installation via `node index.js install flutter-plugin`  
**Future:** Centralized plugin registry with versioning, search, ratings  
**Status:** Out of scope for v1.0
